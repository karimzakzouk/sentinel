# Decision log

Each decision lists what was chosen, why, and what evidence would change it.
The design canvases in `docs/plan/` hold the decisions made before code; this
file records the ones made while building, including where building proved the
plan wrong.

| # | Decision | Why | Revisit if |
|---|---|---|---|
| 1 | Build v2 in the v1 repository; v1 stays on `archive/v1` and the `v1.7.17` tag. | No new setup; history kept. | The project moves to an organization or is renamed. |
| 2 | Keep the name "Sentinel" for now. The Kubernetes API group is `sentinel.karimzakzouk.github.io`, a DNS name the project controls. | API groups should be domains you own; the name is a placeholder, so the group lives in one constant plus generated files. | The final name and domain are chosen. |
| 3 | License: Apache-2.0. | CNCF expects it; it includes a patent grant. | A hosted business model is ever chosen. |
| 4 | Push straight to `main`; CI is the gate; milestones are tagged `v2.0.0-alpha.N` (N = phase). | One builder, fast iteration; protection blocks force pushes and deletion of `main` and `archive/*`. Old v1 tags exist, so v2 builds describe themselves from `v2.*` tags only. | More people start contributing: switch to pull requests with required checks. |
| 5 | The Ledger is SQLite with a persisted hash chain, append-only triggers and projections rebuilt from events. The Merkle log and external checkpoints come in Phase 5. | v1's in-memory chain broke on every restart. SQLite needs no extra service. | Scale needs Postgres, or an audit needs logarithmic proofs before Phase 5. |
| 6 | Every decision point is a slot: one champion engine, shadow challengers on a copy of the input, typed probability outputs checked against their contract, every call recorded or refused, and replay against recorded history. | Engines (including Jev-style models or LLMs) can be added and measured without rewrites, and never act before they are proven. | A slot needs streaming or multi-step outputs the contract cannot express. |
| 7 | Separate identities. The controller reads; the actor patches; the actor lives in its own namespace. | The controller may create (dry-run) pods in its namespace for probes. If the actor's service account lived there too, a compromised controller could start a real pod as the actor. Separate namespaces make that impossible by construction, and the fence makes the controller's pod creates dry-run only. | Kubernetes adds per-verb dry-run RBAC. |
| 8 | Phase 0's fence lets the actor change only replicas (within bounds) and the restart annotation on existing Deployments and StatefulSets in allowlisted namespaces. Everything else in the pod spec is fixed, including images. | An admission policy cannot check "previously deployed", so image rollbacks need their own design. | Phase 2 designs rollbacks (for example, the actor pins a rollback to the digest the old ReplicaSet ran, and the fence admits only digests on an allowlist it is given). |
| 9 | Only the active NetworkPolicy probe can enable the Lab. The probe allows traffic between its own pods, checks a connection succeeds, replaces the allow with a deny, and checks the connection is blocked. | **Whether a cluster enforces NetworkPolicy cannot be read from its configuration.** The same kind v0.33 cluster enforces policy on GitHub's runners and silently does not on the Cursor development VM: kindnet's policy controller needs the kernel's NFQUEUE support and quietly skips enforcement without it. On the VM, traffic passed straight through the Lab namespace's own default-deny policy. The probe got both environments right. | A cheaper signal proves equally reliable. |
| 10 | Each dry-run probe runs in the namespace where its component would run: node agent and eBPF in Sentinel's namespace, user namespaces in a Lab namespace. | Probing everything in the restricted Lab namespace made the node-agent probe fail for the wrong reason. | — |
| 11 | CI tests the probe against plugins with known behavior: Calico (always enforces) and Flannel (never does). kindnet, whose answer depends on the kernel, only has to produce a definite answer. Calico runs in CI only. | The development VM's kernel lacks ipset and NFQUEUE, so Calico cannot run there; Flannel runs everywhere with its `host-gw` backend, which needs no VXLAN. | A local cluster with Cilium is needed for faster iteration. |
| 11a | Test clusters run kube-proxy in nftables mode (except Calico's). | The development VM's kernel lacks the iptables `statistic` match, so iptables-mode kube-proxy cannot load-balance Services with several endpoints: DNS (two CoreDNS pods) silently failed and Online Boutique's services could not find each other. nftables mode works on both the VM and GitHub's runners. | — |
| 12 | Port v1 code in the phase that uses it, not in Phase 0. | The Ledger replaces v1's store; the GitHub client and repo-CI runner belong to the Fixer (Phase 4); error parsing belongs to log fingerprinting (Phase 1). Porting unused code now would ship it untested, along with v1's known bugs (symlink traversal in `ReadFile`, fail-open gates). | — |
| 13 | No Dependabot for now. `govulncheck` runs on every push; dependency bumps happen at phase gates. | Dependabot opened ten pull requests against v1 that nobody merged. | A vulnerability lands between gates and is missed. |
| 14 | CI minutes: the full check runs on every push, the kindnet end-to-end run on code changes, and the Calico run only when the code it covers changes, weekly and on demand. Heavy testing happens on the development VM. | The private repository has about 3,000 Actions minutes a month. | A self-hosted runner is attached (needed by Phase 3 anyway). |
| 15 | The fault-injection harness is a separate binary, and ground truth is written outside the cluster. | Sentinel must never be able to read the answers it is graded against. | — |
| 16 | Sentinel's own pods: restricted Pod Security, read-only root filesystem, no capabilities, distroless non-root image, and a NetworkPolicy allowing only DNS and the API server. | Least privilege for the component that watches everything. | — |
| 17 | The count detector's significance level comes straight from the false-alarm budget: alpha = budget ÷ (ticks per week × fact kinds). This replaces the plan's Benjamini–Hochberg step for count series. | The budget is false alarms per workload per week, the quantity the Phase 1 gate measures, and this split bounds it directly. Benjamini–Hochberg bounds the share of false discoveries among the discoveries made, which says nothing about weekly false alarms on a quiet cluster. Consecutive windows overlap, so the bound is conservative. | The soak shows recall suffers from the conservatism; then calibrate alpha on soak data. |
| 18 | Events that happened before the controller started are not facts. The informer's initial list, and any event last seen before start, only set the baseline. | After a restart, an hour of old readiness-probe failures counted as new and opened false incidents. | Sentinel must explain incidents that began before it started. |
| 19 | Incidents are keyed by workload and resolve after a quiet gap (`detection.incidentGap`, default 5 minutes) with no open episode. The plan's learned gap and grouping across connected workloads wait for the dependency map (Phase 1, slice 3). | A crash loop's fact kinds start and stop at different times. Resolving when the last episode ended split one crash loop into two incidents. | Scoring shows separate faults merged into one incident, or one fault split into several. |
| 20 | Only a workload's latest template change is credited with failing pods on the newest revision; its older template changes are credited with failures on older revisions. | A revert is itself the latest change. Crediting every template change with the newest revision's failures let the revert take the blame for the incident it was fixing. | — |
| 21 | While any series of a workload is in an episode, none of that workload's series learns. | During an OOM incident, the crash-loop facts were too sparse to be significant on their own. Freezing only the alerting series let them leak into the crash-loop baseline, so a later crash loop looked normal. | Long incidents starve unrelated series of learning; then freeze only the series that move with the alerting one. |
| 22 | A container that exited non-zero, in a pod that will restart it, counts as crash-looping whatever the back-off status says. | On Kubernetes 1.37 (kind v0.33), a crashing container spends most of its back-off as terminated with reason Error, and shows CrashLoopBackOff only briefly. Counting only CrashLoopBackOff missed the crash-on-start scenario. | — |
| 23 | The classifier sees every fact kind in the workload's window, not only the significant ones, and only changes made since the workload's last incident resolved. | An OOM incident opened as crash-on-start: the single OOM kill was not significant on its own, and the previous scenario's image change and revert still counted as recent changes. | Calibration (slice 6) shows sub-threshold facts mislead more than they help. |
| 24 | Log access is its own capability (`detect.logs`); without it Sentinel watches from Kubernetes facts alone. | Reading logs was part of the watcher's required permissions, so a cluster denying `pods/log` lost all detection. | — |
| 25 | Logs are fetched on triggers within a budget (30 a minute, two at a time, 300 lines and 64 KiB each), summarized and redacted where they land, and recorded only when they join an incident. | Raw lines must never reach the permanent Ledger, and logs of workloads that never have an incident need not be kept at all. Redaction fails closed: provider formats, structured credentials, secret-named keys and random-looking strings; 46 canary secrets never survive, and the end-to-end test checks the exported Ledger. | Following log streams (tier 1) needs more throughput than the redactor's 20 MB/s per core. |
| 26 | "New error after deploy" compares the new revision's first minutes with the old revision's last five, sampled before the rollout replaces it. It tests a rate ratio above 2, not above 1, at 10⁻³ per rollout with Bonferroni across the errors tested. | Faults that leave pods ready (a misspelled dependency) are invisible to Kubernetes facts. Before-versus-after is cheap (the kubelet keeps the old pods' logs while they exist) but confounded by traffic changes; requiring a doubling keeps ordinary drift and tiny relative increases from alarming. | Concurrent comparison (old and new pods at the same time, as in canaries) becomes available in phase 2. |
| 27 | Scenario runs on the development cluster use a one-minute detection window. | Short windows make incidents resolve soon after a revert, so scenarios run back to back. The cost: a fault that recurs slower than the window, like an OOM kill every two minutes, never puts two facts in one window and is missed. The default five-minute window catches it; slice 4's persistence detectors are the real answer. | Slice 4 lands, or the scoring slice needs the production window. |
| 28 | A Service losing every ready endpoint is a fact on the workloads behind it, but only after Sentinel has seen it with endpoints. | Scaling Redis to zero fails no pod; the empty Service is the only Kubernetes-level trace, and it names the cause directly. Requiring prior endpoints keeps Services that are empty by design (scaled-to-zero environments) from alarming at startup. | Intentional scale-downs alarm too often; then weigh who made the change. |
| 29 | The dependency map starts from configuration: literal environment values and arguments naming a Service. ConfigMap and Secret values are not read. | Cheap, available everywhere, and right for Online Boutique's every edge. Sentinel never caches ConfigMap contents (decision 5's privacy line), so addresses kept there are missed until logs and traffic add edges. | Scoring shows missed edges matter; then add log-derived edges (slice 4) before eBPF. |
| 30 | Undoing a culprit depends on its kind: a rollback for a template change, `scale.restore` for a scale change. | Rolling back a Deployment's template does not bring back replicas a scale change removed. | — |
| 31 | `brain.localize` ranks root causes from evidence ratios (own anomaly, upstream position, recent change, a healthy dependency's unlikelihood); grouping a downstream symptom into its upstream incident waits for slice 4. | Every current scenario raises its incident on the root cause, so grouping could not yet be tested live; slice 4's log-rate detectors produce the downstream symptoms it needs. | — |
