# Decision log

Each decision lists what was chosen, why, and what evidence would change it.
The design canvases in `docs/plan/` hold the decisions made before code; this
file records the ones made while building, including where building proved the
plan wrong.

| 2 | Keep the name "Sentinel" for now. | 3 | License: Apache-2.0. | CNCF expects it; it includes a patent grant. | A hosted business model is ever chosen. |

| 5 | The Ledger is SQLite with a persisted hash chain, append-only triggers and projections rebuilt from events. The Merkle log and external checkpoints come in Phase 5. | v1's in-memory chain broke on every restart. | 6 | Every decision point is a slot: one champion engine, shadow challengers on a copy of the input, typed probability outputs checked against their contract, every call recorded or refused, and replay against recorded history. | Engines (including Jev-style models or LLMs) can be added and measured without rewrites, and never act before they are proven. | A slot needs streaming or multi-step outputs the contract cannot express. |
| 7 | Separate identities. The controller reads; the actor patches; the actor lives in its own namespace. | The controller may create (dry-run) pods in its namespace for probes. If the actor's service account lived there too, a compromised controller could start a real pod as the actor. Separate namespaces make that impossible by construction, and the fence makes the controller's pod creates dry-run only. | Kubernetes adds per-verb dry-run RBAC. |
| 8 | Phase 0's fence lets the actor change only replicas (within bounds) and the restart annotation on existing Deployments and StatefulSets in allowlisted namespaces. Everything else in the pod spec is fixed, including images. | An admission policy cannot check "previously deployed", so image rollbacks need their own design. | Phase 2 designs rollbacks (for example, the actor pins a rollback to the digest the old ReplicaSet ran, and the fence admits only digests on an allowlist it is given). |
| 9 | Only the active NetworkPolicy probe can enable the Lab. The probe allows traffic between its own pods, checks a connection succeeds, replaces the allow with a deny, and checks the connection is blocked. | **Whether a cluster enforces NetworkPolicy cannot be read from its configuration.** The same kind v0.33 cluster enforces policy on GitHub's runners and silently does not on the Cursor development VM: kindnet's policy controller needs the kernel's NFQUEUE support and quietly skips enforcement without it. On the VM, traffic passed straight through the Lab namespace's own default-deny policy. The probe got both environments right. | A cheaper signal proves equally reliable. |
| 10 | Each dry-run probe runs in the namespace where its component would run: node agent and eBPF in Sentinel's namespace, user namespaces in a Lab namespace. | Probing everything in the restricted Lab namespace made the node-agent probe fail for the wrong reason. | — |
| 11 | CI tests the probe against plugins with known behavior: Calico (always enforces) and Flannel (never does). kindnet, whose answer depends on the kernel, only has to produce a definite answer. Calico runs in CI only. | The development VM's kernel lacks ipset and NFQUEUE, so Calico cannot run there; Flannel runs everywhere with its `host-gw` backend, which needs no VXLAN. | A local cluster with Cilium is needed for faster iteration. |
| 11a | Test clusters run kube-proxy in nftables mode (except Calico's). | The development VM's kernel lacks the iptables `statistic` match, so iptables-mode kube-proxy cannot load-balance Services with several endpoints: DNS (two CoreDNS pods) silently failed and Online Boutique's services could not find each other. nftables mode works on both the VM and GitHub's runners. | — |
| 12 | Port v1 code in the phase that uses it, not in Phase 0. | The Ledger replaces v1's store; the GitHub client and repo-CI runner belong to the Fixer (Phase 4); error parsing belongs to log fingerprinting (Phase 1). Porting unused code now would ship it untested, along with v1's known bugs (symlink traversal in `ReadFile`, fail-open gates). | — |
| 13 | No Dependabot for now. `govulncheck` runs on every push; dependency bumps happen at phase gates. | Dependabot opened ten pull requests against v1 that nobody merged. | A vulnerability lands between gates and is missed. |
| 14 | CI minutes: the full check runs on every push, the kindnet end-to-end run on code changes, and the Calico run only when the code it covers changes, weekly and on demand. Heavy testing happens on the development VM. | The private repository has about 3,000 Actions minutes a month. | A self-hosted runner is attached (needed by Phase 3 anyway). |
| 15 | The fault-injection harness is a separate binary, and ground truth is written outside the cluster. | Sentinel must never be able to read the answers it is graded against. | — |
| 16 | Sentinel's own pods: restricted Pod Security, read-only root filesystem, no capabilities, distroless non-root image, and a NetworkPolicy allowing only DNS and the API server. | Least privilege for the component that watches everything. | — |
| 17 | The count detector's significance level comes straight from the false-alarm budget: alpha = budget ÷ (ticks per week × fact kinds). This replaces the plan's Benjamini–Hochberg step for count series. | The budget is false alarms per workload per week, the quantity the Phase 1 gate measures, and this split bounds it directly. Benjamini–Hochberg bounds the share of false discoveries among the discoveries made, which says nothing about weekly false alarms on a quiet cluster. Consecutive windows overlap, so the bound is conservative. | The soak shows recall suffers from the conservatism; then calibrate alpha on soak data. |
| 18 | Events that happened before the controller started are not facts. The informer's initial list, and any event last seen before start, only set the baseline. | After a restart, an hour of old readiness-probe failures counted as new and opened false incidents. | Sentinel must explain incidents that began before it started. |
| 19 | Incidents are keyed by workload and resolve after a quiet gap (`detection.incidentGap`, default 5 minutes) with no open episode. The plan's learned gap and grouping across connected workloads wait for the dependency map (Phase 1, slice 3). | A crash loop's fact kinds start and stop at different times. Resolving when the last episode ended split one crash loop into two incidents. | Scoring shows separate faults merged into one incident, or one fault split into several. |
| 20 | Only a workload's latest template change is credited with failing pods on the newest revision; its older template changes are credited with failures on older revisions. | A revert is itself the latest change. Crediting every template change with the newest revision's failures let the revert take the blame for the incident it was fixing. | — |
| 21 | While any series of a workload is in an episode, none of that workload's series learns. | During an OOM incident, the crash-loop facts were too sparse to be significant on their own. Freezing only the alerting series let them leak into the crash-loop baseline, so a later crash loop looked normal. | Long incidents starve unrelated series of learning; then freeze only the series that move with the alerting one. |
| 22 | A container that exited non-zero, in a pod that will restart it, counts as crash-looping whatever the back-off status says. | On Kubernetes 1.37 (kind v0.33), a crashing container spends most of its back-off as terminated with reason Error, and shows CrashLoopBackOff only briefly. Counting only CrashLoopBackOff missed the crash-on-start scenario. | — |
| 23 | The classifier sees every fact kind in the workload's window, not only the significant ones, and only changes made since the workload's last incident resolved. | An OOM incident opened as crash-on-start: the single OOM kill was not significant on its own, and the previous scenario's image change and revert still counted as recent changes. | Calibration (slice 6) shows sub-threshold facts mislead more than they help. |
| 24 | Log access is its own capability (`detect.logs`); without it Sentinel watches from Kubernetes facts alone. | Reading logs was part of the watcher's required permissions, so a cluster denying `pods/log` lost all detection. | — |
| 25 | Logs are fetched on triggers within a budget (30 a minute, two at a time, 300 lines and 64 KiB each), summarized and redacted where they land, and recorded only when they join an incident. | Raw lines must never reach the permanent Ledger, and logs of workloads that never have an incident need not be kept at all. Redaction fails closed: provider formats, structured credentials, secret-named keys and random-looking strings; 46 canary secrets never survive, and the end-to-end test checks the exported Ledger. | Following log streams (tier 1) needs more throughput than the redactor's 20 MB/s per core. |
| 26 | "New error after deploy" compares the new revision's first minutes with the old revision's last five, sampled before the rollout replaces it. It tests a rate ratio above 2, not above 1, at 10⁻³ per rollout with Bonferroni across the errors tested. | Faults that leave pods ready (a misspelled dependency) are invisible to Kubernetes facts. Before-versus-after is cheap (the kubelet keeps the old pods' logs while they exist) but confounded by traffic changes; requiring a doubling keeps ordinary drift and tiny relative increases from alarming. | Concurrent comparison (old and new pods at the same time, as in canaries) becomes available in phase 2. |
| 27 | Scenario runs on the development cluster use a one-minute detection window. | Short windows make incidents resolve soon after a revert, so scenarios run back to back. The cost: a fault that recurs slower than the window, like an OOM kill every two minutes, never puts two facts in one window and is missed. The default five-minute window catches it; slice 4's persistence detectors are the real answer. | Slice 4 lands, or the scoring slice needs the production window. |
| 28 | A Service losing every ready endpoint is a fact on the workloads behind it, but only after Sentinel has seen it with endpoints. | Scaling Redis to zero fails no pod; the empty Service is the only Kubernetes-level trace, and it names the cause directly. Requiring prior endpoints keeps Services that are empty by design (scaled-to-zero environments) from alarming at startup. | Intentional scale-downs alarm too often; then weigh who made the change. |
| 29 | The dependency map starts from configuration: literal environment values and arguments naming a Service. ConfigMap and Secret values are not read. | Cheap, available everywhere, and right for Online Boutique's every edge. Sentinel never caches ConfigMap contents (decision 5's privacy line), so addresses kept there are missed until logs and traffic add edges. | Scoring shows missed edges matter; then add log-derived edges (slice 4) before eBPF. |
| 30 | Undoing a culprit depends on its kind: a rollback for a template change, `scale.restore` for a scale change. | Rolling back a Deployment's template does not bring back replicas a scale change removed. | — |
| 31 | `brain.localize` ranks root causes from evidence ratios (own anomaly, upstream position, recent change, a healthy dependency's unlikelihood); grouping a downstream symptom into its upstream incident waits for slice 4. | Every current scenario raises its incident on the root cause, so grouping could not yet be tested live; slice 4's log-rate detectors produce the downstream symptoms it needs. | — |
| 32 | The scorer (slice 6) and the read-only UI (slice 5) came before the rate detectors (slice 4). | The gate is a measurement: without `harness score`, no change to the detectors could be shown to help or hurt, and every later slice is judged by it. The UI was asked for, and the explanations it shows already existed in the Ledger. | — |
| 33 | A detection on a workload joins the open incident of a workload it depends on when localization ranks that workload first; an incident whose cause turns out to be in another incident merges into it. Symptoms that only the workload itself can cause (image pulls, configuration errors, unschedulable pods, OOM kills, memory pressure) never blame a dependency. | One fault, one incident: Redis scaled to zero must not also open incidents on the cart service and the frontend. Joining needs the same evidence as localization, so it uses it, and an incident that opened on a symptom first must still end up with its cause. This replaces decision 31's wait for slice 4. | Scoring shows wrong joins (independent faults merged), or slice 4's symptoms arrive before their cause often. |
| 34 | The UI and its API are read-only and listen on loopback inside the pod; `kubectl port-forward` is the way in. The server answers only to loopback Host headers. | Phase 1 has no user accounts, and port-forward makes Kubernetes RBAC (the `pods/portforward` permission) the access control, with nothing exposed to the network. The Host check stops DNS rebinding from a browser on the forwarding machine. | Phase 2 adds actions to the UI; then it needs authentication (OIDC or TokenReview), audit and CSRF protection. |
| 35 | Incidents left open when the controller stops are taken back when it starts, not closed: each starts quiet and resolves after the incident gap unless its workloads' trouble returns. Baselines are not kept across restarts. | A restart used to leave incidents open forever, and new detections on their workloads opened duplicates. Keeping the baselines would need snapshots in the Ledger; until restarts are shown to cost detections, relearning (with the warm-up of decision 36) is simpler. | The soak shows restarts losing detections or alarming afterwards. |
| 36 | Every minute, each workload's errors are sampled from one ready pod's last minute of logs, rotating through its pods, as low-priority fetches within the log budget; each error record is a `log.errors` fact. Error series need at least twice their expected count as well as significance to alarm, end when back under 1.5 times it, take a weak prior instead of the pooled one, learn for 30 minutes before they may alarm, and are learned anew after an hour at one level. | Faults that leave pods up (a dependency gone, traffic finding a bug) were invisible outside rollouts. One pod at a time keeps the count a per-pod rate that scaling does not change, and costs one fetch per workload a minute. Error volumes are large and bursty: with much history the Gamma–Poisson predictive is near Poisson, so a fifth more errors would be significant; a workload's usual level is its own, not the near-zero the pooled prior expects; and an episode on a level that holds would never end, freezing the workload's baselines. | The soak's false alarms come from error series; then model overdispersion and seasonality (SPOT, as slice 4 plans) instead of the ratio floor. |
| 37 | A new class, `runtime.errors`: errors at an unusual rate with pods up and no change to blame. Sentinel escalates it. | Without it, an error-only incident would be forced into a crash or deploy class and could be rolled back for nothing. | — |
| 38 | Error samples skip pods in their first two minutes (or the sample interval, if longer), and a sample joins an incident only when it shows an error the incident has not recorded and the workload's samples did not hold before the incident. | Startup logs warnings and errors that are no rate: Redis brought back by a revert counted 22 errors in its first sample. Live, the frontend's alarm attached six samples at once, several holding only its routine "env platform is invalid" line. | A fault that shows only in a new pod's first minutes is missed; then sample young pods and compare with the template's startup baseline. |
| 39 | The scorer treats a run whose mitigation is to do nothing (a deleted pod its Deployment replaces) as quiet, like a control, and lets fault runs claim the incidents they explain before quiet runs count false alarms. | The first scored session counted the pod deletion as a missed fault, and the next scenario's incident, opened four seconds after a control ended, as the control's false alarm. | — |
| 40 | Rollbacks: the controller names the revision to undo in an `ActionRequest`; the actor, a separate small process running as its own identity, checks that the revision is still the newest, reads the previous revision's template from the Deployment's own ReplicaSet and writes it; the fence lets the actor change a Deployment's pod template and nothing else in its spec. StatefulSet templates stay fixed. | No admission policy can check that a template ran before, so decision 8's fence could not admit rollbacks at all. The controller parses untrusted text all day; it now holds no write on any workload, and the worst it can ask for is an earlier revision of the same workload. The cost: for template content, the actor's code is trusted rather than the fence, so it stays small. | Kubernetes admission gains a way to check a write against existing objects, or the actor's code grows past a small core. |
| 41 | An action is verified when every signal of its incident has ended within ten minutes of the actor's report; otherwise it is recorded as unverified and left to people. Slice 1 does not undo an unverified action automatically. | Phase 1's signals already describe the incident (endpoints, readiness, crashes, error rates), so their end is the user-facing recovery these two actions can claim. Undoing a rollback re-deploys the version that was failing, which is rarely what a person wants; the undo path needs the guards of slice 2 first. | Slice 2 lands breakers and budgets; or traffic signals allow a concurrent control. |
| 42 | The SentinelPolicy's quiet period after a person's edit is enforced as a precondition instead of a timer: the actor acts only if the workload is still exactly as the decision saw it (its newest revision, its replicas). | A bad deploy is itself a person's edit, so a quiet period after any human edit would block every rollback of one. What the quiet period protects, a person already working on the workload, shows as a change after the decision, which fails the precondition and escalates. | People want Sentinel to hold off on workloads they touched recently even when nothing failed. |
| 43 | Until owner adapters exist, the actor refuses plain actions on workloads Argo CD (tracking annotation) or Flux (its labels) keeps in sync, and says so; Helm-installed workloads count as plain. | A plain rollback of a GitOps-managed workload is undone at the next sync, so Sentinel would fight the owner and the fix would not hold. Helm does not reconcile; a plain rollback holds until the next upgrade, which is the drift the Fixer's pull request removes. Argo CD's legacy instance label is not used: Helm charts set the same label. | Slice 4 adds the Argo CD and Flux adapters (pause or suspend, roll back through the owner, resume). |
| 44 | Through Argo CD, a rollback first removes the Application's automated sync, noting what it was on the Application, then rolls the Deployment back as a plain rollback does. A separate policy action (`argocd.rollback`) allows it, the fence lets the actor make that change and no other, and resuming is a person's step (`sentinel resume`), after fixing Git. | A plain rollback under automated sync is undone at the next sync; rolling back through Argo CD's own history would need its API and a token, and still be reverted unless sync is paused. Pausing is one precise write the fence can bound, the Deployment's own ReplicaSets keep the rollback's template safe as for plain workloads, and Argo CD reports the drift instead of fighting it. Resuming before Git is fixed would re-apply the fault, so Sentinel does not resume on its own. | Phase 4's Fixer opens the revert pull request; then resuming after its merge can be Sentinel's step. |
| 45 | Through Flux, a rollback first suspends the Kustomization that applies the Deployment (from kustomize-controller's labels), unless another manager owns the Kustomization's `spec.suspend` (a parent Kustomization setting it would resume it); a Flux HelmRelease's workloads are left to people. Applications an ApplicationSet generates are paused only if the ApplicationSet ignores differences in their sync policy. | Each case is one the design names: a parent reconciling the child's suspend, an ApplicationSet rewriting the Application, and helm-controller's own rollback of a failed upgrade racing Sentinel's. Managed fields say exactly who owns `spec.suspend`, so the check is precise rather than a guess from labels. | HelmRelease remediation is read well enough to defer to it, or Sentinel learns to roll a release back through helm-controller. |
| 46 | The Lab is developed and tested where NetworkPolicy is enforced: in CI (kindnet on GitHub's runners, and now Cilium alongside Calico) and on the self-hosted runner, not on the development VM. | Cilium was the hope for the VM (decision 11), but its kernel lacks VXLAN, ipset and netfilter targets Cilium's datapath still needs, even with native routing, kube-proxy replacement, eBPF masquerading and its iptables rules off: pods start, but the kubelet cannot reach them, so the active probe never decides. `hack/kind-up.sh` keeps a Cilium option, which CI proves on a normal kernel. | The development VM's kernel changes, or the self-hosted runner arrives. |
| 47 | The Lab proves its seal with a prober pod that tries every destination and writes one line per probe to its termination message; the matrix is built from the live cluster (API server Service and endpoints, cluster DNS, every kubelet, the production twins' Services and pods, cloud metadata, the internet by IP) and includes positive controls that must answer. | Reading results from the pod's status needs no `pods/exec`, a permission that would let the Lab run anything in any pod it can see. Building the matrix from the cluster tests the addresses that actually exist, and the positive controls tell "refused" from "the probe never ran". On Flannel the same matrix caught sixteen leaks, which is the proof it can tell. | A destination class is found that the matrix misses (IPv6 on dual-stack clusters is next). |
| 48 | The Lab runs as its own identity, separate from the controller and the actor. Its writes stay in its pool of namespaces; its pods run only the probe image, without a service-account token or volumes other than empty directories; its NetworkPolicies may name only pods of the same namespace. It reads Services, pods and endpoints only in `default`, `kube-system` and the watched namespaces. Before an experiment it proves enforcement with the active probe (a proof lasts ten minutes) and fails closed without it. | The Lab starts real pods, which the controller may only dry-run (decision 8), so it needs a writer; a separate identity keeps that right away from the process that parses untrusted logs all day. The fence bounds a compromised Lab: it cannot start other code, carry a token, or open its own seal. Reading pods cluster-wide would expose every pod spec, environment variables included. Proving the seal with traffic rather than reading policies catches a policy someone else adds: in CI's enforcing clusters an extra allow-all policy must fail the experiment. | Slice 2 starts copies of production workloads in the Lab: the image rule must then widen to images the twins already run, under the same token, volume and policy rules. |
| 49 | A leak to an address outside the cluster (cloud metadata, the internet) fails the seal like any other, and the verdict says so and tells the operator to block those addresses at the nodes. CI expects Calico and Cilium to refuse them; on kindnet it expects the Lab to refuse the cluster when they leak. | On GitHub's runners kindnet enforces NetworkPolicy inside the cluster, yet a Lab pod reached both Azure metadata addresses (169.254.169.254 and 168.63.129.16) through the default-deny policy; Calico and Cilium refused them. Metadata services hand out cloud credentials, so a Lab that can reach them is not sealed, whatever its policies say. No NetworkPolicy can deny an address, so the Lab cannot close this itself. | kindnet applies egress policy to those addresses, or the Lab gains a guard at the node. |
| 50 | A world's pods run production's images, pinned to the digests production runs. What bounds a copy is not its image: it carries no service-account token, mounts only empty directories, ConfigMaps and its own metadata, runs under Pod Security `restricted` and the Lab's quota, and sits behind a seal the Lab cannot open (decision 48). The Lab never reads a Secret: secret values become placeholders and secret volumes empty directories, each recorded as a fidelity difference. | Decision 48's image rule could not hold once the Lab copies workloads, and no admission policy can check that an image is one production runs. Copies of production code may do anything inside the Lab, so the seal must be what contains them; the fence keeps it shut and keeps credentials out. A canary Secret in the end-to-end app proves no secret value reaches the Lab. | Slice 4's shape-preserving fake Secrets, which must be generated without reading the real ones. |
| 51 | Each world gets a Lab DNS: CoreDNS serving one authoritative root zone with each copied Service's short and production names at its Lab address, so copies' configuration resolves to the Lab unchanged; every other name gets NXDOMAIN, and each query is logged. A name the world asked for that the Lab does not provide is recorded as a fidelity difference. | Lab pods cannot reach cluster DNS, and rewriting configuration would change what is tested. The hosts plugin answers unknown names with SERVFAIL, which ends musl's search-path walk: Alpine images then fail to resolve full Service names, as a check with Alpine and Debian showed; a zone answers NXDOMAIN, as cluster DNS does. CoreDNS's template plugin cannot add a catch-all after hosts, since plugin order is compiled in. The log catches dependencies the topology map cannot see, such as addresses in ConfigMaps. | Workloads need SRV records, per-pod names of headless Services, or names under other namespaces' Services. |
| 52 | A Lab verdict rests on three e-processes per candidate, each a product of bets valid however long the Lab runs and whenever it stops: *better*, over blocks where the baseline and the candidate disagree, against "no better than the failing revision"; *works* and *fails*, over the candidate's own runs, against "works at most" and "at least three times in four". PASS needs *better* and *works* at α over the K candidates, once the failure has reproduced and every control has failed; FAIL needs *fails*; anything else at the budget is NOT SURE. | The Lab decides when to stop as evidence arrives, which breaks fixed-sample tests; Ville's inequality bounds an e-process at every stopping time. A test of disagreeing blocks alone never moves when the candidate fails exactly like an always-failing baseline, so it could never FAIL one; the candidate's own record can. Requiring both tests to reject keeps PASS within its share of α without another split. Simulated: a clear fix passes in 13 to 15 blocks, a non-fix fails in 3, and at the edge of the null 3.4% of candidates pass at α = 5%. | The self-hosted runner's repetitions show the false-PASS rate above α on real workloads, or flaky baselines need a bound other than three in four. |
| 53 | A run's oracle: the copy must become ready within a minute and then stay ready for twenty seconds without a restart. The deletion control replaces every container of the failing copy with the probe image doing nothing, keeping the copy's probes; if it passes, the oracle cannot tell a fix from a disabled workload and every verdict is NOT SURE. | Readiness is the signal Kubernetes and phase 1's detection already trust for these faults, and crash-on-start and bad configuration show in it. A workload without a readiness probe is ready as soon as it starts, so its deletion control passes and the Lab says it cannot tell, rather than passing anything that starts. | Faults that only show in traffic or logs: slice 4's replay and the error-log signal join the oracle. |
| 54 | When Sentinel proposes rolling back a Deployment revision it blames, the controller asks the Lab, once per incident, whether the revision before it fixes the failure, whatever the namespace's policy allows; the verdict joins the incident in the Ledger and the UI, and reaches whoever is asked to approve. A Lab that cannot run says NOT SURE, never that the fix failed; Failed is the race's verdict, or, for a prove Experiment, a seal that does not hold. | A rollback an approver can see verified, fifteen runs against fifteen, is the Lab's point; verifying in observe mode too shows what acting would have done and builds the record autonomy needs. The fence lets the controller create only verification Experiments in the Lab's pool. On a cluster the Lab refuses, telling an approver that the rollback does not help would be false. `lab.verifyRollbacks` turns it off where tests drive the Lab themselves. | A policy lets a Lab verdict gate an action, and waiting for the Lab before acting needs a bound. |
| 55 | The actor and the Lab are ready only once they see every namespace they serve, and stop after a minute if they cannot, naming the namespaces; their Deployments restart when their configuration changes, as the controller's does. | The actor kept a watch list Helm had replaced, waited forever on a namespace it no longer had rights in, and reported ready while carrying out nothing; no action was due during the soak, so nothing showed it for two hours. A process that cannot do its job should fail where Kubernetes shows it. | |
| 56 | Every pod a world starts, copies and race variants alike, first runs a seal gate: an init container that holds its containers until the Lab DNS answers and the API server does not, three times running, and fails the experiment NOT SURE if that never happens within a minute. | CI's verbose logs confirmed decision 49's suspicion: on kindnet a new pod reached the API server, cluster DNS, every kubelet and production's pods in its first moment, and nothing ten seconds later. The window is intermittent, so a proof can miss it and let a copy's code start unsealed, connecting to production as it boots. A gate in each pod closes the window for that pod whatever the proof saw; it costs a second or two where policy applies at once. | Network plugins apply policy before a pod's first packet, everywhere the Lab runs. |
